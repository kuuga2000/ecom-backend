## Architecture and cart model

Use **separate `carts` and `cart_items` tables**. A cart is an editable shopping session; it is not an `orders` row with `status = DRAFT`. Orders and immutable order-item snapshots belong to a later milestone.

Implement one active, persistent cart per authenticated customer. A cart item refers to **one exact product variant by `variantId`** and stores its quantity. The customer must select the complete variant before adding it. For example, a product with color and size options requires the ID of the specific `Red / M` variant; the backend must not guess a variant from `Color=Red` alone.

Use Flyway migrations with appropriate foreign keys, a uniqueness constraint for the active cart per customer, a uniqueness constraint for `(cart_id, variant_id)`, and useful indexes. Make a deliberate choice about whether cart item rows store any display snapshots; the current catalog must remain the authority for the displayed price and variant status. Document the choice.

Use `BigDecimal` for money. Follow the catalog's existing currency and decimal rules; if they are undefined, establish and document one consistent convention. Never use floating-point arithmetic for prices.

## API

Implement these endpoints using the project's existing response and error conventions:

- `GET /api/cart` — return the authenticated customer's cart. If no cart exists, return an empty cart representation **without writing to the database**.
- `POST /api/cart/items` with `{ "variantId": 123, "quantity": 2 }` — create the cart on the first add if necessary, then add the exact variant. If the variant is already present, increase its quantity. The new total quantity must still pass validation. Explain that repeating this POST intentionally increases quantity; it is not an idempotent request.
- `PATCH /api/cart/items/{itemId}` with `{ "quantity": 3 }` — set the item's quantity to exactly 3.
- `DELETE /api/cart/items/{itemId}` — remove the item. Define and document the response for a successful deletion.

All endpoints require a valid Milestone 4 bearer token. Derive the customer ID from the validated authentication context; never accept a customer ID from the request body as the cart owner. Scope item lookups and changes to the authenticated customer's cart. Return `404` for an item that does not belong to that customer, without revealing whether another customer owns it.

Return cart item ID, variant ID, SKU, product name, selected option values, quantity, current unit price, line subtotal, and whether the item is currently purchasable. Return total quantity and **estimated subtotal** for the cart. Include a clear reason when an existing line cannot currently be purchased, such as an inactive product or variant.

## Validation and pricing

On add or quantity update:

- Require an existing variant belonging to an active product, with the variant itself active.
- Accept only a positive integer quantity and enforce a documented maximum per line. Check the resulting quantity when an add increases an existing line.
- Accept `variantId` as the merchandise identifier. Do not accept a parent product ID or partial option values as a substitute for selecting a variant.
- If the project already has inventory availability, apply its existing rules. If inventory does not exist yet, do not invent stock values or claim that adding to cart reserves stock.

Calculate display prices and estimated totals on the server from the current catalog price. Do not trust client-supplied prices, SKUs, names, option values, or totals. If a catalog price changes, the next cart read must reflect the current price. Clearly state that checkout will validate price and availability again before creating an order.

An item already in the cart may later become inactive. Keep it visible so the customer can identify and remove it, mark it as not purchasable, and do not include it as an apparently purchasable item. Define and test whether the estimated subtotal excludes such lines, and make the response unambiguous. Preserve referential integrity so a deleted catalog record does not leave an unreadable cart line.

## Transactions and concurrency

Create or update cart lines transactionally. Handle two simultaneous first adds for one customer and two simultaneous adds of the same variant without duplicate carts, duplicate lines, or lost quantity increments. Use PostgreSQL constraints together with an appropriate locking or retry strategy. Do not rely on an in-memory lock that works only in one application instance.

Keep database queries reasonably efficient when rendering a cart; avoid a query per item for its product and selected options.
